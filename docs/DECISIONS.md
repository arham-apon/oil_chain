# Decisions & Deviations

| # | Decision | Reason |
|---|----------|--------|
| D1 | Repo root is `oil_chain/` (the spec's `fuel-ops-platform/`). | Existing git repo. |
| D2 | Local dev venv uses Python 3.13 (only version installed); code targets 3.12 (Docker base `python:3.12-slim`) and avoids 3.13-only features. | No 3.12 on the dev machine. |
| D3 | Simulator returns `sim_time` **without timezone** (`2026-01-01T00:00:00`), though the guide shows `+00:00`. `timeutil.parse_sim_time` treats naive values as UTC. | Observed against the live image. |
| D4 | Retry backoff is hand-written (full jitter) rather than `tenacity`, so POST retries can guarantee an identical body/key and metrics hook in cleanly. | Spec §7.2 |
| D5 | Simulator 200 and 201 on POST /v1/allocations are both treated as success (C4). | Spec C4 |
| D6 | Circuit breaker counts a call that exceeds its timeout as one failure toward the consecutive-failure threshold (it does not trip on a single slow call). | Spec §7.4 wording ("or calls exceeding the timeout") is ambiguous. |
| D7 | Ingestion tags every snapshot with the tick read from `/v1/instance` at the *start* of the sync. When the simulator runs at 8 ticks/s, a station read may already belong to tick t+1. Demand history carries exact ticks, so training data is unaffected; only the snapshot→tick join can be off by one. | REST offers no atomic multi-endpoint read. |
| D8 | A sync requires `instance`, `depots`, `stations`, `routes` (else `SyncError`, nothing written, previous snapshot stays the latest). `events`, `allocations`, `metrics` are optional — a failure/invalid payload there yields a partial sync plus an alert. | Keeps snapshots internally consistent while tolerating a flaky non-critical endpoint. |
| D9 | Malformed-data guard: schemas require all three fuels in every inventory/capacity map, reject negative volumes and unknown enum values. A rejected payload raises `DATA_INVALID` (rate-limited to one alert / 30 s / endpoint), increments `sim_payload_invalid_total{endpoint}`, and the last valid rows stay the latest. | Spec §9.3. |
| D10 | SSE "connected" is set when the server answers 200 (not on the first event): a paused simulator only sends comments, so event-based detection would wrongly trigger the polling fallback. | Found while designing the worker; `SimClient.stream(on_connect=...)`. |
| D11 | Simulator reset (SSE notice "Simulation reset", or the tick going backwards) wipes the *mirror* tables (ticks, snapshots, supply, events, demand, allocations, metrics, forecasts) and publishes `sim.reset`. `decisions`, `audit_log`, `alerts`, `incidents`, `ai_calls`, `model_registry` are never deleted. | Old ticks would otherwise collide with the restarted timeline. |
| D12 | Safety-net heartbeat sync every 10 s (1 s while stale), independent of ticks. | A paused simulator can still change (events/faults injected, allocations created); SSE alone would miss stale-flag clearing. |
| D13 | Windows/Hyper-V on the dev machine reserves TCP 5433-5532 and 8081-8180, so Docker cannot publish 8101-8104 / 8081 / 5433. Container ports stay per spec; host ports are overridable (`INGESTION_HOST_PORT`, `POSTGRES_HOST_PORT`, `REDIS_HOST_PORT`). Postgres is published on `127.0.0.1:55432` by default so it never clashes with a local PostgreSQL on 5432. | Observed `bind: forbidden by its access permissions`. |
| D14 | `constraints.txt` pins the versions installed in the dev venv; Dockerfiles install with `-c constraints.txt`. `DATABASE_URL` for containers is composed from `POSTGRES_*` in `docker-compose.yml` (single source of truth for the password). | Spec §6 (pin versions) and C11 (no hardcoded secrets). |
| D15 | Not yet solved (Phase 5): the `supply_arrivals` table stores only the latest quantity, so "arrival quantity reduced (shortfall)" detection needs a first-seen quantity — plan a migration `0002` (`first_quantity`) before decision-svc detection. | Spec §11.8 vs §8 schema. |
| D16 | **Demand generator verified empirically** (see `docs/MODEL_REPORT.md` §1): the §10.1 formula holds (mean ratio 1.00); jitter is multiplicative with std ≈ noise/√3; the documented busy windows (`07–09`, `16–20`, …) are **inclusive of the last hour**; the hour comes from the row's own `sim_time`; an event covers ticks `start_tick … end_tick` **inclusive** (a 24-tick spike affects 25 ticks). Encoded in `fsp_shared.demand` and `world_constants.HOUR_FACTORS`. | Measured over 480 ticks with two injected spikes. |
| D17 | Heteroscedastic forecast σ: the per-tick σ is `σ_rel × mean` (σ_rel = validation RMSE ÷ mean validation prediction) instead of a constant number of litres. `model_registry` / `PairForecast.residual_sigma` still report the RMSE in litres. | Noise is multiplicative, so a constant σ overstates night-time uncertainty ~3× and inflates stockout risk. |
| D18 | **The demand multiplier is applied structurally.** The regression target is `y / mult`, lag features (EWMAs, momentum) are computed on `d / mult`, and the served forecast is `mult_future × model(...)`. `demand_multiplier` / `event_active` stay in the feature set. The training/serving multiplier comes from `sim_events` (exact, complete), not from sparse, possibly tick-shifted `station_snapshots` (deviation from spec §10.2, which suggested snapshots). | A first version fitted on `y` directly lifted a scheduled ×1.8 spike by only ×1.4 when trained on spike-free history — and judges inject spikes into a spike-free baseline. Caught by `test_scheduled_spike_in_events_raises_forecast_and_risk`. |
| D19 | **Residual learning:** the ridge predicts `y_norm − baseline` (`baseline` = the §10.1 calendar formula without the multiplier), and the serving predictor adds the baseline back. Alpha grid extended to `1e5`. | Heavy shrinkage then falls back to the documented formula rather than a flat mean; never worse than fitting `y_norm` directly over 6 seeds × 12 pairs. |
| D20 | **Honest accuracy claim:** the ridge beats the last-value naive forecast on 12/12 pairs (~40 %), and matches the documented-formula baseline within noise (wins ~7/12, never > 5 % worse; mean MAE 4.05 vs 4.06 L/tick). The formula *is* the generator, so it is the Bayes floor; "beats both baselines for every pair" is not attainable in expectation. Reported as-is in `MODEL_REPORT.md`. | Spec §10 acceptance vs. the measured generator. |
| D21 | Forecast-svc reads only Postgres (via a 0.5 s / event-driven in-memory snapshot) — request handlers never query the DB. The refresher wakes on Redis `state.updated` / `event.changed` / `allocation.changed` / `sim.reset` (falls back to polling if Redis is down). | Keeps `/forecast` for 12 pairs at ~1 ms and lets a new spike show up within 1 tick. |
| D22 | Demand history can trail the snapshot tick (slow sync runs every 8 ticks). The forecaster recurses from the newest observed tick and drops the steps up to "now" so the horizon always starts at `tick + 1`; demand rows newer than the snapshot are ignored. Ingestion additionally catches demand history up on every heartbeat while it is behind (found live: a paused simulator left the last ticks unsynced). | Found by the live acceptance test. |
| D23 | Retraining is scheduled off the tick of the *last attempt* (`Trainer.last_train_tick`), not the active model's tick, so a losing candidate cannot cause a retrain every scheduler pass; after a simulator reset it retrains once on the new timeline. New versions activate only if they beat the active bundle on the candidate's validation slice. | Found by the live acceptance test (versions trained 35 ticks apart after a reset). |
| D24 | `GET /forecast?station_id=&fuel_type=&horizon=` exists next to `POST /forecast`. On Docker Desktop for Windows, a POST whose headers and body arrive in separate TCP writes stalls ≈ 40 ms in the port proxy (delayed ACK) — the service itself answers in ≈ 1 ms in-container. The p95 assertion uses GET; POST numbers are reported with the caveat. | Measured: POST-with-body 49 ms vs empty POST / GET / single-write POST ≈ 2 ms. |
| D25 | Model artifacts are joblib pickles produced and loaded only by the service itself from the `models` volume (`MODEL_DIR`, default `/models`), never from user input. | joblib is the spec's persistence format. |
